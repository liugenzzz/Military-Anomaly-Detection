# 问答形态设计：方位指代 / 坐标 / 轮数 / 图数（v0.5）

修正 `docs/12`、`docs/13` 中的三处问题，并补上反同质化的配比矩阵。

---

## 一、核心修正：问法的动词决定答案形态

实测验证（Qwen3-VL 上的行为）：

| 提问 | 模型实际给出的答案 |
|---|---|
| 「红色框的飞机出现在画面的**什么位置**？」 | 「位于画面的**左上角**。紧靠图像上边缘和左边缘，大约在画面宽度的 3%–15%、高度的 8%–27% 区间内」 |

**问「什么位置」，模型答的是方位描述，不会吐 `[x1,y1,x2,y2]`。** 所以 `docs/13` 里
主线轮 2 写成「该异常出现在画面的什么位置？→ 位于 [312,168,704,395]」是自相矛盾的，
这种样本会逼模型学一个反常识的映射。

### 结论：定位任务拆成两个，问法池严格分开

| 子任务 | 占定位任务 | 问法必须含 | 问法禁止含 | 答案形态 |
|---|---|---|---|---|
| **`locate_verbal` 方位指代** | **70%** | 什么位置 / 哪一块 / 什么方位 / 靠近哪条边 | 框出 定位 坐标 边界框 标注 圈出 检测框 | 自然语言方位 |
| **`locate_box` 坐标框** | **30%** | 框出 / 定位 / 边界框 / 坐标 / 标出 | 什么位置 在哪 方位 | `[x1,y1,x2,y2]` |

**为什么方位指代占七成**：我们做的是**异常检测**，不是目标检测。输出应当是值班人员看得懂的
态势描述，而不是一串坐标。坐标保留三成，是因为下游系统对接需要结构化输出，但不该占主导。

## 二、能稳定出框的问法池

关键是**动词**。参考项目 `_shared/ask_describe.txt` 里那条 `#! forbid: 坐标 框出 框住
检测框 边界框 标出 定位 圈出 找出` 就是反向印证——描述轮要禁掉这些词，正是因为它们
一出现模型就会去输出框。

### `locate_box` 问法池（这些能稳定出框）

```
框出画面中的集结区域。
请给出火点的边界框坐标。
以 [x1,y1,x2,y2] 格式输出烟雾区域的位置。
定位画面中越界的车辆，给出坐标。
标出异常区域的边界框。
请用边界框标注该处火光。
输出集结区域的归一化坐标。
把烟雾覆盖的范围框出来。
检测并框出画面中的异常区域。
请以坐标形式标注出异常所在区域。
给出该异常区域的四点坐标。
用检测框圈出画面中的军机群。
```
**共同点**：动词是「框出 / 标出 / 定位 / 输出坐标 / 圈出 / 标注」，且大多显式点明
「坐标」或「边界框」或直接给出 `[x1,y1,x2,y2]` 格式。**格式在问句里点明，答案才稳定。**

### `locate_verbal` 问法池（这些只会得到方位描述）

```
这处异常在画面的什么位置？
集结区域处在画面的哪一块？
火点靠近画面的哪条边？
烟雾出现在画面的什么方位？
越界目标现在大致在什么位置？
异常区域大概占据画面的哪个部分？
从整幅画面看，这处异常在什么方位上？
异常出现在画面的上半部还是下半部？
这片区域相对画面中心是偏向哪边的？
说明异常所处的大致方位。
```

### 方位指代的答案该怎么写

学你截图里模型的自然表达方式，**三档粒度混着用**：

| 粒度 | 样例 |
|---|---|
| **九宫格档** | 「在画面左上角」「位于画面中部偏右」「靠近画面下缘」 |
| **比例档** | 「横向约在从左往右三成到五成之间，纵向处在上缘往下五分之一处」 |
| **参照档** | 「紧贴画面上边缘，距左边缘约一个目标宽度」 |

建议配比：九宫格 40% / 比例 35% / 参照 25%。三档混用能让模型学会在不同精度要求下作答，
而不是只会说「左上角」。

## 三、反同质化：四个维度的配比矩阵

「不要所有的都很同质化」需要落到可执行的配比上。四个维度独立采样：

### 维度 1 · 轮数

| 形态 | 占比 | 说明 |
|---|---|---|
| **单轮** | **50%** | 一问一答。保证模型能独立响应单条指令 |
| **双轮** | 30% | 判定 → 追问方位，或 判定 → 追问依据 |
| **三轮** | 20% | 判定 → 方位 → 描述（完整主线） |

（此前定的「主线/单轮五五开」按你的意见保留：**多轮合计 50%、单轮 50%**。）

### 维度 2 · 图数

| 形态 | 占比 | 用在哪 |
|---|---|---|
| **单图** | **80%** | 聚集、爆炸、烟雾、正常的绝大部分 |
| **多图（2–4 帧）** | 20% | 越界移动**全部**；另加少量爆炸/烟雾的「前后变化对比」 |

多图的额外用法（不只是越界）：
```
Q: <image><image>这两帧间隔约 10 秒，画面中的烟雾发生了什么变化？
A: 烟柱明显增高并向右偏斜加剧，覆盖范围由原来的约六分之一扩大到近四分之一，
   浓度也有所上升，说明燃烧仍在持续。
```
数据来源：ERA 同一视频的多帧、XD/UCF 同一事件段的多帧。**这类题只有多帧才做得出来**，
是单图任务无法覆盖的能力。

### 维度 3 · 问法风格

| 风格 | 占比 | 样例 |
|---|---|---|
| 提问式 | 35% | 「画面中是否存在异常？」 |
| 指令式 | 30% | 「请分析该画面并说明异常类型。」 |
| 角色式 | 15% | 「作为值班分析员，判断是否需要上报。」 |
| 格式指定式 | 12% | 「用 JSON 输出，字段为 anomaly / region / evidence。」 |
| 追问式 | 8% | 「刚才说的那处火光，具体亮到什么程度？」（仅多轮内） |

### 维度 4 · 答案形态

| 形态 | 占比 | 说明 |
|---|---|---|
| 自然段 | 55% | 2–3 句连贯描述 |
| 短答 | 20% | 「是。装备集结。」「9 架。」 |
| 分点 | 12% | 「依据有三：一是…二是…三是…」 |
| 坐标 | 8% | `[x1,y1,x2,y2]` |
| JSON | 5% | 结构化输出，供下游系统对接 |

## 四、修正后的主线样例

### 三轮主线 · 方位指代版（占三轮主线的 70%）

```
轮1  Q: <image>这张画面中是否存在异常？是什么类型的异常？
     A: 存在异常，为装备集结。

轮2  Q: 集结区域处在画面的哪一块？                      ← 改成方位问法
     A: 在画面上部偏中，横向大致从左往右四分之一到七成，纵向靠近上缘往下
        五分之一处，下方约三分之二的画幅是空置地面。

轮3  Q: 这些目标是怎么排列的？
     A: 九架飞机排成两列，前列五架、后列四架，机头统一朝向西南方，
        列内间距基本一致，整体呈规则阵列。
```

### 三轮主线 · 坐标版（占三轮主线的 30%）

```
轮1  Q: <image>画面中有无异常？属于哪一类？
     A: 有，为火光异常。

轮2  Q: 请框出该处火光，以 [x1,y1,x2,y2] 给出坐标。      ← 明确要坐标
     A: [421,388,533,502]

轮3  Q: 描述一下这处火光的亮度特征。
     A: 火焰整体呈明亮橙红色，核心接近白色，向外过渡为橙色与暗红色，
        与周边深色地表形成强反差，是全图最亮的区域。
```

### 双轮 · 判定 + 依据（不涉及位置）

```
轮1  Q: <image>画面中是否存在异常？
     A: 存在，为烟雾。

轮2  Q: 依据是什么？
     A: 存在一片边界模糊、半透明的灰白色区域，呈自下而上的柱状扩散，
        下窄上宽，遮挡了后方地表纹理，符合烟羽特征，区别于云层与地面雾气。
```

### 单轮 · 各种形态混合

```
Q: <image>画面中是否存在异常军事活动？
A: 是。九架军用飞机在停机坪密集列队，符合装备集结特征。

Q: <image>请分析该画面，用 JSON 输出结果。
A: {"anomaly": "massing", "subtype": "equipment", "region": [312,168,704,395],
   "evidence": "9 架军用飞机规则列队、间距均匀", "confidence": "high"}

Q: <image>烟雾出现在画面的什么方位？
A: 在画面左上方，横向占据从左缘往右约四成，纵向从上缘延伸到画面中部偏上，
   紧贴左上角。

Q: <image>框出画面中的越界车辆。
A: [214,388,266,436]、[402,371,455,419]、[578,392,631,441]
```

## 五、对 `docs/13` 的修改

需要改的是所有主线轮 2 与 `position` 侧面的样例：**问「什么位置」的，答案不能给坐标**。
`docs/13` 里 `position` 侧面的样例本来就是方位描述（写对了），但主线轮 2 写成了坐标，
按本文改成方位问法即可；要坐标的另起一版用 `locate_box` 的问法。

坐标在整个数据集里的出现频率：约占全部 QA 的 **8%**（定位任务 12% × 坐标版 30%
＋ JSON 输出里的 region 字段）。符合你说的「尽量少出现，偶尔出现可以」。

## 六、坐标规范：对齐参考项目的 `bbox_2d` 格式

### 输出格式

坐标答案一律写成 **Qwen-VL 原生格式**，不用裸列表：

```json
单框  {"bbox_2d":[588,392,611,459],"label":"军用飞机"}
多框  [{"bbox_2d":[214,388,266,436],"label":"车辆"},{"bbox_2d":[402,371,455,419],"label":"车辆"}]
```

三个理由：基座模型预训练时见过这个形状，学起来更快；带 `label` 让定位与分类一次答完；
机器可解析，review 与一致性校验能直接正则提取。

`extra` 里同时记录 `coordinate_mode: "qwen_relative_1000"`、`bbox_scale: 1000`、
`image_width`、`image_height`，下游不必猜。

### 换算链路：像素做中转，不直接归一化到归一化

```
各数据集原始标注  ->  像素 [x1,y1,x2,y2]  ->  0~1000 整数 bbox_2d
                     ↑ 越界裁剪在这一步做
```

中间必须过一遍像素，是为了**让越界裁剪在像素域完成，与标注软件的行为一致**
（这条约定取自参考项目 `core/coords.py`）。已验证：同一个归一化框在 1360×765 与
4000×3000 两种原图尺寸下，算出的 `bbox_2d` 完全相同。

### 归一化 / 像素的自动判别

九个数据集的坐标约定各不相同：

| 数据集 | 原始格式 |
|---|---|
| Mendeley、MAR20-Roboflow | YOLO 归一化 `[cx,cy,w,h]`，0~1 |
| FASDD | COCO 像素 `[x,y,w,h]` |
| MAR20 官方 | VOC 像素 `[xmin,ymin,xmax,ymax]` |
| DOTA | 像素四点多边形 |
| VisDrone | 像素 `[x,y,w,h]` |
| DroneCrowd | 像素点坐标 |

**把归一化当像素（或反过来）不会报错，只会静默产出一堆错框。** 所以
`tools/ds/boxes.py` 提供两个自检函数，`prepare.py` 每次跑完自动执行：

- `infer_coord_mode()` —— **按整批框判断**而非单框：单个 `[0,0,1,1]` 两种约定下都合法，
  但一整批全 ≤ 1.0 就几乎不可能是像素
- `audit_scene_boxes()` —— 检查五类问题并告警：归一化误当像素、坐标值落在 1.0~2.0
  的模糊区、框超出图像边界、`x1>=x2`（多半是把 `[x,y,w,h]` 当成了 `[x1,y1,x2,y2]`）、
  超过一半的框占满整幅画面

### 顺带的优化：图像尺寸读文件头

`image_size_fast()` 只读 PNG/JPEG/BMP 的文件头拿宽高，不解码像素，实测比 PIL 快约
2 倍且结果完全一致（41 张图零差异）；冷门格式回落 PIL。遍历几万张图时这个差别很实际。
