---

## 一、三条设计原则

### 1. 多标签，不是单选

一个画面可以同时挂多个标签。这不是为了灵活，是因为**现实本来如此**：

```
一架关闭应答机、正在逼近边界的飞机
  -> 电磁/伪装/关闭应答机  +  空中/越界/抵近边界线
爆炸现场
  -> 地面/征候/爆炸火光    +  地面/征候/烟雾
```

### 2. 二级分「行为」与「征候」两族 —— 这是整个体系的骨架

| 族 | 是什么 | 判读依据 | 单帧能不能判 |
|---|---|---|---|
| **行为类** | 主体在**做什么** | 需要运动、过程、上下文 | ⚠️ 大多不能，需多帧/时序 |
| **征候类** | 客观**存在什么** | 画面里看得见的物理现象 | ✅ 能 |

**为什么必须分开：**「集结」「侦察」「伪装」都是带意图的动作，而意图要从**变化**里
读出来。单帧影像只能给你一个瞬间的构型 —— 一排停着的车和一支停下来的车队，
像素上没有区别。硬把行为类当单帧任务做，就是教模型编造。

征候类相反：烟就是烟，弹坑就是弹坑，一帧足够。

### 3. 领域怎么判 —— 必须有明确规则，否则标签噪声无穷

- **行为类**：领域 = **行为主体所属的作战域**，不按它当时的物理位置。
  停机坪上的军机仍属 `空中域`（它是空中力量），不因为停在地上就变成地面。
- **征候类**：领域 = **现象发生的位置**。
  舰船上的火情属 `水面域`，野外的火情属 `地面域`。

## 二、一级：领域

| id | 名称 | 范围 | 主要感知手段 |
|---|---|---|---|
| `air` | 空中 | 固定翼、旋翼、无人机、导弹 | 光学 / 雷达 |
| `sea` | 水面 | 水面舰艇、潜艇（上浮）、港口 | 光学 / SAR / AIS |
| `land` | 地面 | 装甲、车辆、人员、工事、设施 | 光学 / SAR |
| `em` | 电磁 | 雷达、通信、导航、应答机 | **非影像**：ESM / SIGINT |

> **`em` 域是非影像任务。** 火控雷达开机、关闭应答机这类，光学影像里看不见。
> 放进 schema 是为了体系完整、将来接入多源情报时不用重构；
> **但 VQA 数据集这一轮填不了它，标注来源得是信号情报。**

> 太空域、网络域不纳入本体系 —— 与航拍/监控影像这个输入形态无关。

## 三、二级：行为族（8 类）

| id | 名称 | 定义 | 判读要点 |
|---|---|---|---|
| `massing` | 集结 | 力量向某处汇聚、密度显著高于常态 | **汇聚过程**，不是静态密集停放 |
| `maneuver` | 机动 | 成建制移动、转场、输送 | 队形 + 位移方向 |
| `incursion` | 越界 | 越过边界/进入禁区/抵近敏感目标 | 需要边界的先验位置 |
| `recon` | 侦察 | 盘旋、徘徊、抵近观察、异常航线 | **轨迹形态**，单点位置说明不了 |
| `concealment` | 伪装隐蔽 | 伪装网、假目标、掩体、静默 | 与常态对比，或前后对照 |
| `fortify` | 工事构筑 | 阵地开设、壕沟、掩体、新建设施 | 前后对照最可靠 |
| `coordination` | 协同 | 多实体同步活动、多兵种混编 | 多目标的时空关联 |
| `logistics` | 补给保障 | 物资囤积、装卸、加油、弹药转运 | 场站 + 反复往返 |

## 四、二级：征候族（5 类）

| id | 名称 | 定义 | 单帧可判 |
|---|---|---|---|
| `fire` | 火情 | 明火、烟雾、爆炸火光 | ✅ |
| `damage` | 毁伤 | 弹坑、残骸、建筑坍塌、烧蚀痕迹 | ✅ |
| `concentration` | 密集分布 | 目标密集停放/驻留（**不判断是否为集结**） | ✅ |
| `disaster` | 灾害 | 洪涝、滑坡、垮塌、事故现场 | ✅ |
| `infra_change` | 设施变化 | 新增/拆除/扩建（需前后对照） | ⚠️ 需配对 |

> **`concentration`（密集分布）与 `massing`（集结）必须分开**，这是整个体系里最容易
> 出错的一对。停机坪上排列整齐的军机、停车场里的车队 —— 它们在**构型**上和集结
> 完全一样，区别只在「是不是正在汇聚」。前者是可观测的客观事实，后者是行为判断。
> 混为一谈，就是教模型看见任何军用机场都报警。

## 六、标签格式

```json
"labels": [
  {"domain": "land", "family": "indicator", "type": "fire",   "event": "smoke"},
  {"domain": "land", "family": "indicator", "type": "fire",   "event": "explosion"}
]
```

扁平写法（便于检索与统计）：`land/indicator/fire/smoke`

**每一条标签还要带证据来源**，这一轮踩坑踩出来的硬要求：

```json
{"domain":"land", "family":"activity", "type":"massing",
 "event":"装备集结",
 "evidence": {"source":"annotation|rule|model",   ← 标注自带 / 规则推的 / 模型判的
              "rule":"density_cluster",
              "verified_by":"free_look"}}          ← 有没有被自由看图验证过
```

## 七、需要你拍板的四个点

1. **行为族 8 类**是否合适？我在你的 5 类基础上加了 `maneuver`（机动）、
   `fortify`（工事构筑）、`logistics`（补给保障）—— 这三个在 ISR 口径里是独立的
   活动类别，且都是真实的预警指标。

2. **征候族 5 类**是否认可？特别是把 `concentration`（密集分布）单列 ——
   它是「看着像集结但不是」的正面标签，而不只是负样本。

3. **`em` 域**确认进 schema，但标注来源是信号情报而非影像。
   这一轮 VQA 数据集是否直接标注「本轮不填」？

4. **三级事件的粒度** —— 现在每个二级下 2~5 个具体事件。
   要更细（便于精确判读）还是更粗（便于凑够样本量）？

定完这四点，我出 `configs/ontology.yaml` 的正式版，然后才去评估家底能填哪些格。
